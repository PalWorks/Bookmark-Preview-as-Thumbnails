# Design: Agent bridge (coding agents work on your Chrome bookmarks, with review and Undo)

## Problem Statement

Coding agents and IDEs (Claude Code, Cursor, VS Code) cannot see or organise the bookmarks in a person's real Chrome. The owner asked: "can we create a CLI / local MCP bridge via which Coding Agents / IDEs can operate on the bookmarks present in a chrome browser?" This is an open-source feature of Visual Bookmark Manager with Thumbnail Previews (AGPL-3.0 plus a commercial licence).

## What Makes This Cool

An agent can propose "tidy my Research folder": 9 moves, 3 renames, 2 to Trash. You see the proposal as a before/after list with previews, untick anything you disagree with, and apply it as one step that one click undoes. Nothing changes until you say so. Other bookmark MCP servers give agents raw write access; this one makes agent edits reviewable and reversible, using the Trash and Undo the extension already has.

## Constraints

- Chrome only lets an extension change bookmarks (`chrome.bookmarks`). Editing the Bookmarks file while Chrome runs is lost or blocked, and it bypasses sync.
- No new install warning for existing users (rule D3 in DECISIONS.md). `nativeMessaging` shows "Communicate with cooperating native applications" when it is required.
- Chrome starts the native host itself; MCP clients start their own servers. So the host must act as a broker that MCP servers connect to (the common pattern in existing projects).
- The extension's service worker owns every write (Trash, Undo, folder prefs, metadata allowlist); the bridge must go through it, never around it.
- Owner preferences: plain, mobile-first UI; few GitHub Actions runs; AGPL-3.0 plus commercial licensing; no keys in anything shipped.

## Premises

1. Agents work through the extension's `chrome.bookmarks`, never the Bookmarks file.
2. The reason to build this, when open-source bookmark MCP servers already exist: our users already have the extension (one install), and every agent edit lands in our Trash and Undo with tags, ratings and previews. Safety is the headline; without it, people should use an existing project.
3. Read-only by default. An agent may only propose changes if the user allows proposals for that agent; nothing is written until the user approves a proposal in the extension; deletes go to Trash; proposals are capped; every applied change appears in the extension with Undo.
4. (Revised after the second opinion.) The goal is an optional `nativeMessaging` permission, asked only when the user turns the bridge on, so there is no install warning. Step one is a spike that proves optional `nativeMessaging` plus host registration on Chrome 156, Edge and Brave. If the spike fails, we stop and decide afresh; a localhost connection with pairing would be its own design, not a ready fallback.
5. One npm package (CLI, MCP server, native host). `npx <package> install` registers the host for Chrome, Edge and Brave on Windows, macOS and Linux. AGPL-3.0 plus commercial licence, like the extension.

Our half: worker-owned writes through existing Trash/Undo paths, read-only default, pairing, per-agent write permission, caps, audit, preview-aware dry-run diffs, install testing per browser.

## Approaches Considered

### Approach A: Read-only bridge
Spike, then the package with read tools only (tree, list folder, search, item details). Effort M, low risk. Ships fastest; does not deliver organising.

### Approach B: Reviewed change sets (chosen)
A first, then agents propose change sets reviewed in an "Agent changes" panel and applied as one Undo-able step, with an activity list. Effort L/XL in two milestones, medium risk.

### Approach C: Direct writes with an activity log
Immediate capped writes for allowed agents, each undoable afterwards. Rejected: mistakes happen before review, and it is close to what existing projects do.

## Recommended Approach

Approach B, in two milestones.

**Milestone 1: spike and read-only bridge**
1. Spike (gate for everything else): a throwaway branch adds `nativeMessaging` to `optional_permissions`, requests it from a click, and registers a minimal host. Pass criteria, each recorded per browser:
   - `chrome.runtime.connectNative` works after the grant on Chrome 156, Edge and Brave (Linux first, then Windows and macOS);
   - the host manifest's `allowed_origins` admits the extension in each browser at its real id, written to that browser's host-manifest location (Linux and macOS: the per-browser `NativeMessagingHosts` folder; Windows: the per-browser registry key);
   - an open native port keeps the service worker alive, and the worker reconnects after a browser restart when the switch is on;
   - the install warning is unchanged (compare `management.getPermissionWarningsByManifest`, as for D3).
   Fail on any: stop and decide afresh.
2. Extension: a "Connect coding agents" switch in Settings that requests the permission, shows the pairing state, and can be turned off (removes the permission). The service worker gets a bridge module that holds the native port only while the switch is on, and answers read requests by reusing `bookmark_tree.ts`, link metadata, tags and folder prefs. Folders hidden from search stay hidden from agents.
3. Package (separate npm package, working name `bookmarks-thumbnails-mcp`):
   - native host: started by Chrome, listens on a user-only local socket (Unix socket in a 0700 directory; Windows named pipe restricted to the user);
   - MCP server over stdio: connects to the socket, offers read tools: `list_folders`, `list_folder`, `search`, `get_bookmark` (title, URL, folder path, tags, rating, last opened, preview available);
   - CLI with the same reads (`bookmarks search …`);
   - `npx <package> install` writes the host manifest for each installed browser (Chrome, Edge, Brave) with the extension ids for that browser. Ids: the Chrome Web Store build is `eedekafhclngkhhkcocblnllkbodgnhj`, which Chrome and Brave install, and Edge too when it installs from the Chrome Web Store. There is no Edge Add-ons listing today; if one is made, its id differs and is added to Edge's manifest. `--extension-id` adds a developer's unpacked id.
4. Pairing and authentication:
   - The socket or pipe is reachable only by the same OS user; that is the outer boundary.
   - A new client connects with a hello naming itself (e.g. "Claude Code"). The extension shows a 6-digit code in Settings and the client prints the same code; the user confirms in the extension. One pending prompt at a time; a prompt expires after 2 minutes; at most 5 prompts an hour, so a local process cannot spam them.
   - On confirmation the extension issues a random 32-byte token for that client. The client stores it in its user config folder in a file only the user can read (mode 0600); the extension stores only its SHA-256 hash in `chrome.storage.local`.
   - Every request carries the token; the host forwards it and the extension checks the hash. A missing or unknown token gets no data.
   - Revocation: removing a client in Settings deletes its hash; its next request is refused.
5. Permission model (one per paired client, set in Settings > Coding agents): **Read** (default after pairing) or **Read and propose**. A `propose_changes` call from a Read client is refused with "This agent may read only. Allow proposals in the extension: Settings > Coding agents." Even with Read and propose, nothing changes until the user approves the proposal in the panel.

**Milestone 2: reviewed change sets**
1. A `propose_changes` tool takes a list of operations (move, rename, set tags, set rating, move to Trash) and returns a change-set id plus a dry-run summary. Nothing changes. Pending change sets live in `chrome.storage.local` (`cs_<id>`, at most 10, each at most 200 operations), so they survive service-worker restarts and browser restarts; a proposal still pending after 24 hours expires. If the host or browser restarts mid-review, the proposal stays in the panel; the agent sees "not connected" until the extension reconnects.
2. The "Agent changes" panel (wireframe: projects/PalWorks-Bookmark-Preview-as-Thumbnails/palani-feat-1.6.0-menu-feedback-sketch-20261109-173941.png): who proposed it; "Nothing has changed yet"; counts; changes grouped by kind with preview, before → after and a tick box; "Apply N changes" and "Reject all"; "Applied as one step. You can undo it from Activity."
3. Apply runs in the service worker as one operation: deletes through the existing Trash (one operation id), moves and renames through the worker using the same DOM-free functions as `bulk_move.ts` and `rename.ts`, and tags and ratings through a new internal entry point that applies the same metadata allowlist as `META_PATCH` (the `META_PATCH` message itself rejects non-page senders and is not used). Each item is re-checked at apply time; an item that changed since the proposal is skipped and reported.
4. Undo journal: today the Undo records for moves and renames are returned to the page and live only as long as a toast (D15). For agent change sets the worker persists its own journal in `chrome.storage.local` (`csj_<id>`): for every applied item, the before and after state (parent and index, title, tags, rating, and the Trash operation id for deletes). Kept 30 days, like Trash, then removed by the existing daily alarm.
5. Activity: every applied change set with one-click Undo. Undo restores each item only if its current state still equals the recorded after-state (the D15 rule: never overwrite a newer change); items changed since are skipped and listed.
6. Limits: proposals only from clients set to Read and propose; at most 200 operations per change set and 10 pending sets; proposals expire after 24 hours.

## Open Questions

- Does optional `nativeMessaging` activate on Chrome 156? (One unconfirmed report says no.) The spike answers it.
- Package name and whether the CLI is the same binary as the host.
- Language for the host: Node (one runtime with the extension's tooling, needs Node installed) or a single Go/Rust binary (no runtime, harder per-OS builds). Recommendation to test in the plan review: Node, distributed through npm, since every target user runs a coding agent that already needs Node.
- Whether the panel opens automatically when a proposal arrives, or shows a badge on the toolbar icon only.
- Firefox is out of scope.

## Success Criteria

- No new install warning for existing users; the permission is asked only when the switch is turned on.
- From Claude Code: `claude mcp add` plus the pairing step lets the agent search and list bookmarks within 2 minutes of installing.
- A 50-change proposal is reviewed and applied in the panel, and one Undo restores every item, including Trash entries, tags and ratings.
- No agent can change a bookmark without the user's approval; an unpaired client gets nothing.
- Works on Chrome, Edge and Brave on Linux, Windows and macOS (tested in that order).

## Distribution Plan

- Extension side ships in a normal release (1.7.0 or later) through the Chrome Web Store, after 1.5.0 and 1.6.0 are live.
- The package ships on npm (`npx <package> install`), source in this repository under `bridge/`, AGPL-3.0 plus commercial licence, SPDX headers.
- Publishing is a manual, owner-approved step (no new GitHub Actions workflow; the existing CI job gains the bridge tests).

### R2-1 — clarity (minor)

**Problem**

> Activity is still presented as a place ('You can undo it from Activity', Milestone 2 step 5) but the design does not say it is a new view, where it lives in navigation, or whether it is limited to agent change sets. The repo has no existing Activity view.

**Remedy**

> State that Activity is a new view, its location (for example Settings > Coding agents or a toolbar menu entry), and that it lists agent change sets only.

### R2-2 — clarity (minor)

**Problem**

> The 2 minute setup criterion and the 50-change review criterion have no stated measurement method, and the Open Question on auto-opening the panel versus a toolbar badge has no default.

**Remedy**

> State how the 2 minutes are timed (for example a manual run from a clean profile) and give a default (badge only) to be revisited in the plan review.

### R2-3 — consistency (minor)

**Problem**

> Milestone 1 step 5 specifies the refusal of propose_changes, but that tool is only introduced in Milestone 2, so Milestone 1 ships a permission setting (Read and propose) that has no effect. The setting is also named 'Settings > Coding agents' while the switch is named 'Connect coding agents'; the relation between the two Settings entries is not stated.

**Remedy**

> Say that the Read and propose choice is shown from Milestone 2 (or is inert in Milestone 1), and state whether 'Connect coding agents' and 'Coding agents' are one Settings section.

### R2-4 — completeness (minor)

**Problem**

> Behavior is unspecified for pending change sets when the proposing client is later set back to Read or removed in Settings, or when the bridge switch is turned off. Nothing is written without user approval, so this is not a safety gap, but the panel behavior is ambiguous.

**Remedy**

> Choose and document: pending sets from a downgraded or removed client are discarded, or stay reviewable but are labelled with the client's changed state.
