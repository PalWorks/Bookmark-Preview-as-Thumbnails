## Problem Statement

Coding agents and AI assistants cannot see or organise the bookmarks in a person's real Chrome. The owner asked: "can we create a CLI / local MCP bridge via which Coding Agents / IDEs can operate on the bookmarks present in a chrome browser?" The review found that the part nobody else offers is the safe review and Undo of AI-made changes, not the transport, and that demand for a live bridge is not yet shown. So the work is staged: first any AI can propose changes through a file or a paste, reviewed and undone in the extension; the live bridge for coding agents follows if people ask for it. This is an open-source feature of Visual Bookmark Manager with Thumbnail Previews (AGPL-3.0 plus a commercial licence).

## What Makes This Cool

An AI proposes "tidy my Research folder": 1 new folder, 9 moves, 3 renames, 2 to Trash. You see the proposal as a before/after list with previews, untick anything you disagree with, and apply it as one step that one click undoes. Nothing changes until you say so. Other bookmark MCP servers give agents raw write access; this one makes AI edits reviewable and reversible, using the Trash and Undo the extension already has, and it works with any AI, from a chat window to a coding agent.

## Constraints

- Chrome only lets an extension change bookmarks (`chrome.bookmarks`). Editing the Bookmarks file while Chrome runs is lost or blocked, and it bypasses sync.
- No new install warning for existing users (rule D3 in DECISIONS.md). Stage 1 adds no permission. Stage 2 adds `nativeMessaging` as an optional permission, requested only when the user turns the bridge on (proved on Chrome 156 and Edge 156, Linux: D17).
- The extension's regular service worker owns every write (Trash, Undo, folder prefs, metadata allowlist) and all bridge state. Nothing writes around it. The bridge and the change-set coordinator load only in the regular worker, never the incognito one (`IS_INCOGNITO_WORKER`, src/sw.ts:20; `"incognito": "split"`, public/manifest.json:24).
- Tags and ratings are keyed by URL (src/lib/storage_index.ts:12): bookmarks that share a URL share them. Ratings are integers 1 to 5, or `null` to clear (`cleanRating`, src/lib/metadata_sanitize.ts:30).
- Owner preferences: plain, mobile-first UI; few GitHub Actions runs; AGPL-3.0 plus commercial licensing; no keys in anything shipped.

## Premises

1. AI changes go through the extension's `chrome.bookmarks`, never the Bookmarks file.
2. The reason to build this, when open-source bookmark MCP servers exist: every AI edit lands in our review panel, Trash and Undo, with tags, ratings and previews. Safety is the headline.
3. Nothing changes without the user. A change set is only a proposal until the user applies it in the panel; deletes go to Trash; sets are capped; every applied set appears in Activity with Undo.
4. Disclosure is scoped. What an AI sees (export or bridge reads) is limited to folders the user picked; Undo cannot take back what was disclosed.
5. Demand is tested before the expensive part. Stage 2 starts only when the demand check in Success Criteria passes.

## Approaches Considered

- **A: Read-only bridge.** Rejected as a first step: copies existing projects and organises nothing.
- **B: Bridge first, then reviewed change sets.** The office-hours choice; changed at the gate (uc1).
- **C: Direct writes with an activity log.** Rejected: mistakes happen before review.
- **D: Reviewed change sets first, fed by export and import; the bridge later as a second way in (chosen at the gate).** One change-set format, one validator, one panel and one apply engine serve every source.

## Stage 1: Agent changes without a bridge (release 1.7.0 or later)

Effort [estimated]: 1a M (human ~2 weeks / CC ~1 day), 1b M (human ~2 weeks / CC ~1 day). Before UI work, run /plan-design-review on the export, import, Agent changes panel and Activity screens (the autoplan Design phase was skipped).

### 1.1 Export for an AI

- Entry: "Ask an AI to organise" in the main menu opens an export sheet.
- The user ticks the folders to include; nothing is ticked at first (uc2). Folders hidden from search (src/lib/folder_prefs.ts:35) and their contents are not offered. A tick box "Remove the part of links after ?" strips query strings and fragments; it is unticked by default.
- The export is JSON: `{format: "bookmarks-thumbnails.snapshot", v: 1, snapshotId, createdAt, folders: [{id, path, count}], items: [{id, parentId, index, title, url?, tags, rating}]}`, plus a short instruction text that tells the AI the change-set format below and asks for JSON only.
- Actions: "Copy for your AI" (clipboard: instructions plus snapshot) and "Save as file". No image bytes are exported.
- The sheet says plainly that the AI's provider will see these titles and links.

### 1.2 The change-set format

- `{format: "bookmarks-thumbnails.changes", v: 1, snapshotId?, title?, ops: [...]}`.
- Operation shapes: `create_folder {tempId: "new:N", parentId, title}`, `move {id, parentId, index?}`, `rename {id, title}`, `set_tags {id, tags[]}`, `set_rating {id, rating}` (1 to 5 or `null`), `trash {id}`. 1a accepts the first three; 1b adds the rest. `create_bookmark` is not offered (d2).
- The format and its validator live in `src/lib/change_set/` and are written first in 1a. Stage 2 imports the same file into the package through a Vite path alias, with a compile test on both sides.

### 1.3 Import and validation

- Entry: "Import changes" in the main menu, and a paste box at the end of the export sheet. Paste or pick a file; at most 1 MB.
- A set is refused whole, with the reason per operation, if it has:
  - an unknown id, or an id outside the folders the snapshot exported, or one hidden from search;
  - the same item twice in one kind of operation, or a trashed item in any other operation;
  - a move of a folder into itself or a descendant, or a move into a folder the same set trashes;
  - a change to a root folder (Bookmarks bar, Other, Mobile) or a managed bookmark (`isManaged`, src/lib/bookmark_tree.ts:70);
  - an unknown, duplicate or cyclic `new:N`, or a `new:N` used before its `create_folder` (only `move.parentId` and `create_folder.parentId` may name one);
  - an `index` outside the target folder's range (an index past the end means "last");
  - a rating other than 1 to 5 or `null`; more than 20 tags, a tag over 40 characters, or a title over 255 characters;
  - different tags or ratings on two ids that share a URL;
  - more than 200 operations, or more than 1,000 nodes affected once Trash descendants are counted.
- Proposals are simulated on a working copy of the tree; a set whose combined effect is invalid (A into B and B into A) is refused.
- Moves out of a folder the set trashes are allowed and always run before the Trash.
- Pending sets live in `chrome.storage.local` as `cs_<id>`: at most 10 pending, each expires after 24 hours.

### 1.4 The Agent changes panel

- Wireframe: projects/PalWorks-Bookmark-Preview-as-Thumbnails/palani-feat-1.6.0-menu-feedback-sketch-20261109-173941.png.
- Shows the source ("Imported from a paste" or the file name, and the set's `title` as text), "Nothing has changed yet", counts, and changes grouped by kind with preview, before and after, and a tick box. A create reads "New folder: <title> in <parent>". Tag or rating changes on a shared URL read "also applies to N other bookmarks with this URL".
- Unticking a `create_folder` also unticks and blocks the moves into it.
- Buttons: "Apply N changes" (primary) and "Reject all". After apply: "Applied as one step. You can undo it from Activity."
- All AI-supplied strings render as text, with control and bidi characters stripped.

### 1.5 Apply, Finish and Undo

- One coordinator in the regular worker runs Apply, Finish and Undo one at a time. Its lease in `chrome.storage.session` stores `lastProgressAt`; a lease with no progress for 5 minutes is cleared only after the coordinator confirms no run is active.
- On Apply the worker first stores an immutable approval record: the baseline per operation, the ticked operation ids, their dependencies and the execution order.
- Order: create folders, moves, renames, tags and ratings, Trash.
- Journal: a header key plus one key per item (`csj_<id>_<n>`) holding the state (`applying`, `done`, `skipped`, `undoing`, `undone`), the before-state and the intended after-state. Each entry is written before its item runs and marked after.
- Per-item re-check before each step: move compares `parentId` (index best effort), rename compares the title, metadata compares the field per URL; earlier operations' expected effects are applied to later operations' baselines. A changed item is skipped and listed; a skipped move cancels any later Trash of the folder it was leaving.
- `create_folder` records its intent before creating and the returned id right after. On resume, an unknown outcome is reconciled only when exactly one new folder with that title appeared under the parent since the intent time; otherwise it is listed for the user.
- Moves use a per-operation `applyMove(id, parentId, index?)` that shares the checks of src/lib/bulk_move.ts; renames share src/lib/rename.ts. Metadata writes go through `StorageIndex.update` (src/lib/storage_index.ts:89) with the conflict check inside its per-URL queue, one journal entry per URL and field. The META_PATCH allowlist is extracted into one function used by META_PATCH and the coordinator.
- Trash (1b): one batch call per set with a durable request id (the `requestId` pattern of src/sw/trash.ts:256-264), the operation id and per-entry results stored in the journal. The descendant set is frozen at approval; a folder whose subtree grew or holds hidden items is skipped and listed, never refreshed and deleted (src/sw/trash.ts:352 refreshes today, so the coordinator uses its own entry point). Restore receipts for these sets are kept 30 days, not the 10 minutes of `RESTORED_KEEP_MS` (src/lib/trash_store.ts:34).
- Interrupted apply: Activity shows "Partly applied: 31 of 50" with Undo for the done items and Finish for the rest. On resume an item still `applying` is re-read: equal to the after-state counts as done, equal to the before-state as not applied, anything else is a conflict and is listed. `cs_<id>` is kept until the set is fully applied, rejected or expired.
- Undo runs in reverse order and restores an item only if its current state still equals the recorded after-state (the D15 rule). Restoring from Trash returns new ids (src/sw/trash.ts:589-591); Undo uses a persisted old-to-new id map and checks storage scope like `inScope` (src/sw/trash.ts:408). A created folder is removed through Trash only if it still has the proposed title and holds nothing the user added. Undo states are `undoing`, `undone`, `partly_undone`; Finish never re-applies undone items; emptying Trash marks affected sets "Undo partly available".

### 1.6 Activity

- A new view, opened from the main menu ("Activity") and from the panel. It lists change sets only: pending, applying, partly applied, applied, undone, rejected, expired; newest first; Undo on applied sets.
- Retention: summaries of rejected and expired sets 30 days; applied journals 30 days, at most 50 sets; a dropped journal's row stays with "Undo no longer available". The existing daily alarm cleans up.

### 1.7 Storage

- New keys (`cs_<id>`, `csj_<id>`, `csj_<id>_<n>`, later `bridge_clients`) never take the legacy metadata shape that `migrateStorageSchema` renames (`isLegacyMetaRecord`, src/lib/storage_migration.ts:30) and stay out of backup export and import (src/lib/backup_manager.ts only copies settings, `thumb_` and `meta_`).
- Stored records carry a schema version, with a migration test from the previous version.

## Stage 2: Coding-agent bridge (only if the demand check passes)

Chrome on Linux and macOS (uc3). Effort [estimated]: L (human ~3 weeks / CC ~2 days). Brave, macOS and reconnect after a browser restart are checked first, before other Stage 2 work.

### 2.1 Shape

- The extension owns all state (pairing, tokens, change sets, journals). The native host is a stateless relay between a user-only local socket and the native port. The MCP server and CLI connect to the socket.
- Extension: one Settings section, "Coding agents", headed by the "Connect coding agents" switch, which requests the optional `nativeMessaging` permission. Below it: the pairing prompt, the paired clients (name, paired date, last used, folders granted, Read or Read and propose, Remove), "Remove all clients" and the host version. Turning the switch off closes the port and removes the permission; pairings are kept.
- If `connectNative` fails or the host exits with an error, the section shows the cause the host reported and "Run `npx bookmarks-thumbnails-mcp install`, then turn this off and on", with a Remove permission button. The worker retries once a minute while the switch is on, and at browser start.
- A proposal arriving from an agent shows a badge with the pending count on the toolbar icon and a dot on the Coding agents section; nothing opens or takes focus. The panel refreshes without losing the user's unticked boxes. Pending sets of a removed or downgraded client, or after the switch is off, stay reviewable with a label.

### 2.2 Package

- One npm package, working name `bookmarks-thumbnails-mcp` (final name fixed before the first publish), Node 22 or later (d1), bundled JavaScript with no native modules. Binaries: `bookmarks-thumbnails-mcp` (MCP server with no command; also accepts every CLI command), `bookmarks-thumbnails` (CLI), `bookmarks-thumbnails-host` (native host). The bin checks the Node version and prints found and required.
- The one command a user types: `claude mcp add bookmarks -- npx bookmarks-thumbnails-mcp@<pinned version>`. On first run the MCP server installs the host when none is installed. It never replaces an installed host: the host copy changes only through an explicit `install`, and a version mismatch is reported by `doctor` and in the hello reply with the exact `install` command. (This settles the conflict between the DX and Eng phases in favour of Eng.)
- `install`: idempotent; copies the host to a per-user folder (Linux `~/.local/share/bookmarks-thumbnails/`, macOS `~/Library/Application Support/bookmarks-thumbnails/`), writes a launcher with the absolute Node path, points the Chrome host manifest at the launcher with `allowed_origins` for `eedekafhclngkhhkcocblnllkbodgnhj` (plus every unpacked copy it finds in the profiles' Preferences, and `--extension-id` for any other). From helper 1.7.1 it also writes the manifest into the data folder of each running Chrome started with `--user-data-dir` that holds the extension, since Chrome reads helpers from there. One OK or FAIL line per browser, `--dry-run`, `--node`, `--manifest-dir`; ends with next steps and snippets for Claude Code, Cursor and VS Code. `uninstall` removes manifests, launcher and stale sockets.
- `doctor` (and `doctor --json`, `doctor --last-error`): host manifest present, allowed ids, launcher and Node path resolve, extension connected and paired, host version, Flatpak or Snap detected as unsupported, each with its fix.
- Socket: `<runtime dir>/chrome-<profileid>.sock`; runtime dir `$XDG_RUNTIME_DIR/bookmarks-thumbnails` (else `/tmp/bookmarks-thumbnails-<uid>`) on Linux and `$TMPDIR/bookmarks-thumbnails` on macOS, mode 0700, checked with `lstat` (real folder, owned by the user) at host start; paths under 100 bytes. The extension sends a random 8-character profile id in its first message; the host opens the socket only after it. Overrides: `BOOKMARKS_THUMBNAILS_RUNTIME_DIR`, `BOOKMARKS_THUMBNAILS_TOKEN_FILE`.
- The host rewrites request ids per connection, drops a closed connection's pending entries, and allows at most 4 connections, 64 KB per request and one in-flight request per unpaired connection. Start failures are sent on the native port and appended to `<data dir>/host.log`.
- Npm publishes with provenance; publishing is a manual, owner-approved step.

### 2.3 Pairing and scope

- A client says hello with its name (at most 64 characters, control and bidi characters stripped, shown as "says it is <name>"). `pair` with no code starts a prompt; the extension shows a 6-digit code only in Settings, with the start time; the user types it into the client (MCP `pair` tool argument, or `pair --code`). The prompt is bound to the starting connection; three wrong codes end it; it expires after 2 minutes; one at a time; at most 5 an hour; the user can cancel it and block that name for an hour.
- At pairing the user picks the folders this client may read (none ticked at first) and whether to strip query strings (uc2). The grant can be changed later in Settings.
- On success the extension sends a random 32-byte token on that connection only; the client stores it in a 0600 file; the extension stores its SHA-256 hash. Removing a client deletes the hash. `NOT_PAIRED` after storage loss or a profile reset makes the client delete its token and ask to pair again. Tokens never appear in errors, `doctor`, `host.log` or JSON output. The pairing code passes through the agent transcript; that risk (2-minute life, 3 tries) is recorded in DECISIONS.md.
- Permission per client: Read (default) or Read and propose. `propose_changes` from a Read client returns `READ_ONLY`.

### 2.4 Tools and protocol

- Messages: JSON `{v, id, type, token?, body}`; first message `hello {protocolVersion, client, package}`, answered with `protocolVersion`, `minClient` and the host version. The extension accepts package versions from `minClient` up, with one minor version of overlap and a deprecation message one release ahead.
- Reads (MCP and CLI with matching names): `list_folders` (`{id, path, count}`), `list_folder`, `search` (title, URL, tags, case-insensitive, relevance then title), `get_bookmark` (title, URL, folder path, tags, rating, last opened, whether a preview exists; no image bytes). `limit` default 100, max 500; opaque cursors expire after 10 minutes and on any tree, folder-preference or metadata change (`CURSOR_EXPIRED`). Every id outside the client's grant or hidden from search behaves as unknown, in every tool and on every page, rechecked at apply time. Reads use an in-memory index built from `meta_` keys and the tree, never `get(null)` (which would load every thumbnail, src/lib/storage_index.ts:30); search under 200 ms on 10,000 bookmarks after warm-up.
- Writes: `propose_changes` takes the Stage 1 change-set format plus an `idempotencyKey` (a repeat with the same payload returns the existing set; a different payload is refused; keys kept 24 hours), returns the set id and the dry-run result. `get_change_set` returns `{id, state, createdAt, decidedAt?, counts, items[{op, state, reason?}]}` and tells agents to poll every 10 seconds. At most 10 pending sets in total, 5 per client.
- Every MCP tool description says bookmark titles and URLs are untrusted data.
- Errors: `{code, message, fix, retry: "after_user_action" | "after_seconds" | "never", retryAfterSeconds?, context, traceId?, docUrl}`. Codes: `NOT_CONNECTED`, `NOT_PAIRED`, `PAIRING_PENDING`, `READ_ONLY`, `INVALID_REQUEST`, `TOO_LARGE`, `RATE_LIMITED`, `CURSOR_EXPIRED`, `AMBIGUOUS_TARGET`, `UPDATE_EXTENSION`, `UPDATE_PACKAGE`, `INTERNAL`. Errors before pairing name the next step in order (switch, then code). MCP errors set `isError`; the CLI writes to stderr with a fixed exit status per code and offers `--json` (default when stdout is not a terminal). A client remembers the profile it paired with and never silently switches.

## Stage 3: More browsers and Windows (when Stage 2 usage justifies it)

## Success Criteria

- No new install warning; Stage 1 adds no permission.
- A 50-change proposal is reviewed and applied in the panel, and one Undo restores every item, including Trash entries, tags and ratings.
