## Problem Statement

A daily user (feature-request email, 2026-11-06) hit gaps compared with Chrome's native
bookmark manager: folder counts ignore subfolders, folders look flat, bookmarks without a
capture show "No Preview", deletes are permanent, there is no way to hide the folder panel,
deleting takes several clicks, and settings cannot be backed up cleanly. Live version is
1.2.0 (Web Store CRX verified identical to `dist/` on 2026-11-07).

Review of the code found three defects that must be fixed before any of this ships:

1. **Update migration destroys local keys.** `migrateStorageIndexKeys` in `src/sw.ts` renames
   every `chrome.storage.local` key that is not `thumb_*`, `meta_*` or `hasSeenWelcome` to
   `meta_<key>` on every update. 1.3.0 is the first update after AI settings shipped, so it
   would move `ai_enc_key` and `ai_api_key_encrypted` (users lose their saved API key) and
   would also eat any new `trash_*` keys.
2. **Recapture drops AI tags.** `persistCapture` and both error paths in `src/sw.ts` call
   `storageIndex.set` with a fresh record that has no `tags`.
3. **Duplicate Finder deletes outside any safety net.** `AISettingsPage.tsx` calls
   `chrome.bookmarks.remove` directly for single delete, group merge and merge-all, and bulk
   paths swallow errors.

## What Makes This Cool

Delete becomes fearless. A visual Trash shows the thumbnail (or site icon) of what you
deleted, its original folder path and when it expires. One Undo reverses a whole operation,
including a Duplicate Finder "merge all". Deletions made in Chrome's own bookmark manager
while this extension's tab is closed are also caught, best effort. Bookmarks that were never
captured still look recognisable thanks to Chrome's local favicon store.

## Constraints

- MV3 service worker can stop at any time: no long timers, no in-memory-only state for
  anything that must survive. Message listeners that respond asynchronously return `true`
  synchronously.
- React Compiler lint rules (`react-hooks/set-state-in-effect`, `preserve-manual-memoization`):
  derive counts during render, keep async work behind `await` in effects, no manual
  `useMemo`/`useCallback` with unpreservable deps.
- New behaviour goes into hooks under `src/popup/hooks/` and libs under `src/lib/`; `App.tsx`
  stays a thin composer.
- Object URL revoke discipline in `useThumbnails` stays intact.
- No new permission warning: `favicon` warning is suppressed when paired with `tabs` (Chrome
  favicon guide), `alarms` has no warning (Chrome permissions list). Both verified 2026-11-07.
- UX rules: one primary action per screen, Undo over confirmation for reversible actions,
  typed confirmation only for irreversible ones, tap targets at least 40px, labels on key
  actions, works at 360px wide, visible focus, full keyboard operation, contrast in both themes.
- `incognito: "split"`: incognito runs a second SW. Assumed to share `chrome.storage.local`
  with the regular profile [Unverified, test on an unpacked build]. Every trash entry is its
  own key, so even shared contexts never rewrite a shared array, and only the regular-context
  SW records external removals.

## Premises (agreed)

1. These are parity gaps against Chrome's native manager; the thumbnail grid stays the core.
2. Per-item delete must not ship without Undo and Trash.
3. Restored items get new IDs and a new `dateAdded` (API limit). Thumbnails and AI tags survive
   because both are keyed by URL (`thumb_<url>`, `meta_<url>`), provided defect 2 is fixed.
   Missing parent folder: recreate it by title from saved ancestry, else fall back to the
   "Other bookmarks" folder in the same storage scope.
4. Same Web Store listing; no new install warning.
5. Trash keeps entries 30 days, auto-purges, offers per-entry Restore and Empty trash.
6. (Added after cross-model review) Defects 1 to 3 above are in scope as prerequisites.

## Cross-Model Perspective

Codex cold read (2026-11-08), verified against code where noted:

- Coolest version: a visual "Recently Deleted" view with thumbnails, breadcrumbs, expiry, and
  one Undo per operation (a merge produces one entry, not dozens).
- Release blockers: the migration (verified), tag loss on recapture (verified), Duplicate
  Finder deletes (verified), `useBookmarkTree` does not subscribe to bookmark events so views
  go stale after external changes (verified: no listeners in the hook).
- Restore must respect storage scope: Chrome now has separate local and account bookmark
  trees; use `folderType` and `syncing`, never fixed IDs or translated names. Never move a
  local bookmark into a synced folder as a fallback.
- Managed and permanent nodes need capability checks in the service, not only disabled menu
  items.
- `bookmarks.onRemoved` gives `node`, `parentId` and `index`; the removed node reportedly
  includes its descendants, which makes external capture cheap. [Unverified until tested.]
- Restore triggers `onCreated`, whose auto-capture handler can recapture; restore must
  suppress it.
- Correction for 1.4.0: `BookmarkTreeNode.dateLastUsed` gives "last opened" without the
  `history` permission.

## Approaches Considered

- **A) Popup-owned trash.** Rejected: misses deletions made outside the extension and races
  between two open extension tabs.
- **B) Service-worker-owned trash.** Chosen.
- **C) Undo-only delayed delete.** Rejected: no recycle bin, and closing the tab within the
  window commits the delete.

## Recommended Approach (B)

### Prerequisites

1. **Migration fix** (`src/sw.ts`). Gate with `storage_schema_version` in
   `chrome.storage.local`; run the legacy rename only when the marker is below 2, and only for
   keys whose value has the legacy `MetadataRecord` shape (`id` and `url` strings equal to the
   key). Then set the marker to 2. On `reason === 'install'` set the marker to 2 directly, so a
   fresh install never runs the legacy rename. Repair pass (runs once per SW start, cheap
   two-key read): if `meta_ai_enc_key` or `meta_ai_api_key_encrypted` exist (from a dev
   build), move them back.
2. **Tag-preserving metadata.** Add `storageIndex.patch(id, partial)` that merges into the
   existing record. All three capture paths in `src/sw.ts` use `patch`.
3. **One delete path.** Every deletion in the UI (context menu, tile and list delete buttons,
   Duplicate Finder single, group and merge-all) goes through the trash service below.

### Trash service

`src/lib/trash_store.ts` (shared types and storage helpers, usable from SW and popup):

```ts
type SavedNode = { oldId: string; title: string; url?: string; dateAdded?: number; children?: SavedNode[] };
type TrashEntry = {
  version: 1;
  entryId: string;          // crypto.randomUUID()
  operationId: string;      // groups roots deleted by one user action
  source: 'extension' | 'external';
  title: string;            // raw root title; the popup formats labels
  bookmarkCount: number;    // bookmarks in this subtree
  deletedAt: number;
  expiresAt: number;        // deletedAt + 30 days
  state: 'prepared' | 'deleted' | 'restoring' | 'restored' | 'failed';
  parentId: string;
  index: number;
  ancestors: Array<{ oldId: string; title: string }>; // root first
  scope: { rootId: string; rootTitle: string; folderType?: string; syncing?: boolean };
  tree: SavedNode;
  restoredIds: Record<string, string>; // oldId -> newId, checkpointed during restore
  error?: string;
};
```

Key: `trash_v1_<entryId>`. Entries are metadata only (no image data); previews come from
existing `thumb_<url>` records or the favicon store.

SW messages (listener returns `true` synchronously):

- `TRASH_DELETE { ids: string[] }` → validate every id first: reject if permanent root
  (`parentId` is `'0'` or missing) or `unmodifiable === 'managed'` (self or any descendant).
  If any id is blocked, remove nothing and respond `{ rejected: [{ id, reason }] }`, so one
  operation is always one Undo. Ids nested inside another selected folder are dropped (the
  parent covers them). Then for each root: `getSubTree`, resolve ancestry by walking
  `parentId`, read scope from the root ancestor (`rootId`, plus `folderType`/`syncing` when
  present); in one `storage.local.set` call persist the entry as `prepared` plus one
  `trash_pending_<nodeId> = { entryId, at }` key for every node in the subtree (one key per
  node, no shared array); `remove`/`removeTree`; mark `deleted`. The pending keys are cleared
  by the `onRemoved` handler when it sees each id, not here, so a late event can never look
  external. The daily alarm also sweeps pending keys older than 5 minutes. If the persist fails, nothing is removed and the error is
  returned. If removal fails, the entry is deleted and the error returned. Responds
  `{ operationId, entryIds, removedCount }`.
- `TRASH_RESTORE { operationId }` or `{ entryId }` → mark `restoring`; resolve the parent in this
  order: (a) original `parentId` if it still exists; (b) deepest surviving ancestor from
  `ancestors`, recreating the missing folders below it by title (before creating a folder,
  reuse an existing child of the resolved parent with the same title, and record the mapping
  in `restoredIds`, so two roots from one missing folder land in one recreated copy); (c) the saved `scope.rootId`
  if it still exists; (d) a permanent folder whose `folderType` and `syncing` match the saved
  scope; (e) the permanent folder whose title equals `ancestors[0].title`; (f) fail with
  "Original location no longer exists" and leave the entry in Trash. Never a hard-coded id.
  An operation restores its roots in ascending original `index`; children are created parents
  first in saved order, `index` clamped to the parent's current child count. Exact position is
  best effort when other siblings changed meanwhile. `restoredIds` is checkpointed after each
  create; the entry is marked `restored` with `expiresAt = now + 10 min` so a repeated Undo is
  a no-op. During a restore the SW sets a module-scope `restoringUntil = now + 60 s` and the
  `onCreated` auto-capture handler skips while it is in the future (a lost value after a SW
  restart costs at most one extra capture). Partial failure leaves `failed` with
  `restoredIds`, shown in Trash with the error and a **Retry** button that continues from the
  checkpoint instead of duplicating.
- `TRASH_EMPTY {}` and `TRASH_DISCARD { entryId }` → delete entries. Never deletes
  `thumb_*`/`meta_*` (another bookmark may share the URL).

`chrome.bookmarks.onRemoved` at SW module scope, registered only when
`!chrome.extension.inIncognitoContext` (bookmark events fire in both split contexts; one
writer avoids duplicate entries):

- If `trash_pending_<removedId>` exists, remove that key and ignore the event. Because every
  node of an extension delete has its own pending key, this works whether Chrome fires one
  event per root or per descendant. No scan of all trash entries.
- If `removeInfo.node` is absent, skip.
- Otherwise write an `external` entry immediately (nothing held only in memory). Grouping uses
  a persisted `trash_ext_op = { operationId, lastAt, rootCount, droppedCount }` record: reuse
  its `operationId` when `now - lastAt < 2 s`, else start a new one. Writes to this record go
  through a single promise queue in the SW (only one SW context writes it). An operation keeps
  at most 200 root entries; beyond that only `droppedCount` increases and the Trash row says
  "and N more not kept". This keeps a sync wipe or bookmark import from flooding storage.
- Never auto-restore external removals.

Incognito: the popup in an incognito window talks to the incognito SW. If Open Question 4
confirms shared `chrome.storage.local` (expected), that SW writes the same per-node pending
keys, so the regular SW's `onRemoved` handler still recognises the delete as the extension's
own. If storage is not shared, delete buttons and the Trash item are disabled in incognito
with the note "Trash works in regular windows only", and the release does not depend on it.

Expiry: `chrome.alarms` `trash-purge`, `periodInMinutes: 1440`, re-created on SW start if
missing; also run the purge when the Trash view opens. Purge removes entries past
`expiresAt`, and `restored` entries past their 10-minute window.

### Popup

- `useTrash` hook: reads `trash_v1_*` keys, subscribes to `chrome.storage.onChanged`, exposes
  `deleteItems(ids)`, `undo(operationId)`, `restore(entryId)`, `discard(entryId)`,
  `empty()`, `lastOperation`.
- `UndoToast` component: bottom of screen, `role="status"` `aria-live="polite"`, text
  "Deleted 'X'" plus an **Undo** button (40px), stays 8 seconds. Ctrl/Cmd+Z triggers Undo while
  visible, unless focus is in an `input`, `textarea` or `contenteditable` (native undo wins
  there). Replaces the `confirm()` in `useContextMenu`. Labels are built in the popup, with titles
  truncated at 40 characters plus an ellipsis; the SW stores raw title and count only.
- `TrashView` (reached from a "Trash (N)" sidebar footer item next to AI Settings, and from the
  TopBar settings menu when the sidebar is hidden; N counts operations not in `restored`
  state): one row per operation, expandable to its entries, each with preview, title,
  original path, "Deleted 2 days ago, removed in 28 days", a **Restore** button per entry
  (primary action), and **Empty trash** that requires typing `EMPTY` (irreversible). Empty
  state: "Nothing in Trash. Deleted bookmarks stay here for 30 days."
- `useBookmarkTree` subscribes to `onCreated`, `onRemoved`, `onChanged`, `onMoved`,
  `onChildrenReordered`, `onImportEnded`; coalesces into one refresh per 150 ms; reruns an
  active search; if the selected folder disappears, navigates to its nearest surviving ancestor.

### Parity items

- **Deep counts (1).** Pure `countBookmarksDeep(node)` in `src/lib/utils.ts`; Sidebar computes
  a count map during render from the tree it already has. Badge tooltip: "N bookmarks,
  including subfolders". Context menu "Open all (N)" keeps the direct-child count because that
  is what the action opens.
- **Yellow folders (2).** CSS tokens `--folder-fill` (#F6C343 light, #E0AE2E dark) with a darker
  `--folder-stroke` (#9A6B00 light, #F6C343 dark) so the icon keeps 3:1 contrast on both
  backgrounds. Applied to sidebar, grid tiles and list rows.
- **Favicon fallback (3).** `faviconUrl(pageUrl, size)` helper building
  `chrome.runtime.getURL('/_favicon/')` with `pageUrl` and `size=32`. New `BookmarkPreview`
  component used by `ThumbnailTile`, list rows and `TrashView`: thumbnail, else the favicon
  (32px, centred on a tinted panel) with the domain under it. `/_favicon/` never errors; for an
  unknown site Chrome returns its generic globe, which is acceptable because the domain text
  still identifies the bookmark. No third branch. Always on; no setting.
- **Sidebar toggle (6).** Button at the left of `TopBar` with label "Folders" and
  `aria-expanded`; hides or shows the sidebar and lets the main content take the full width.
  State `sidebarHidden` in `chrome.storage.sync` via `useSettings`. A narrow-screen overlay
  drawer is deferred to 1.4.0.
- **Delete button (8).** Trash icon button with `aria-label="Delete <title>"` beside the
  existing more-options button on tiles, list rows and folder tiles; `stopPropagation` on click
  and Enter so the tile does not open. Shown on hover and focus for pointer devices, always on
  `(hover: none)` devices. One click deletes and shows the Undo toast.
- **Settings backup (10).** One validated allowlist shared by export and import in
  `backup_manager.ts`: `useIncognito` (boolean), `theme` (enum), `captureDelay` (number,
  100 to 10000), `useActiveTabCapture` (boolean), `sidebarHidden` (boolean), `ai_mode`,
  `ai_provider`, `ai_model`, `ai_custom_tags` (strings), `ai_custom_url` (string, dropped if it
  contains userinfo or a query string). Never the API key or encryption key. New
  "Export settings" action writes `{ version: 1, kind: 'settings', timestamp, settings }` with
  no thumbnail reads; import accepts both kinds.

## Open Questions

1. Does `removeInfo.node` include full descendants for an external folder delete on current
   stable Chrome? Test on the Chrome version installed here; if not, external folder entries
   record the folder only and say so in the UI.
2. Are `folderType` and `syncing` present on this Chrome version? If absent, restore uses steps
   (c) and (e) of the parent lookup.
3. Does `removeTree` fire `onRemoved` once for the root or once per descendant? Either is
   handled: descendants of a pending root are ignored, and external descendants of a buffered
   root are folded into it.
4. Is `chrome.storage.local` shared between split incognito and regular contexts? Determines
   whether Trash in an incognito window shows regular-profile entries.

## Success Criteria

- Updating 1.2.0 to 1.3.0 keeps the saved AI key and settings (migration test).
- Recapturing a preview keeps its AI tags (regression test).
- Every delete path produces a Trash entry; Undo restores titles, URLs, order and folder
  nesting; previews and tags reappear with no recapture.
- A repeated Undo creates no duplicates; a restore interrupted half way can be retried.
- Permanent and managed nodes cannot be deleted by any path.
- Entries older than 30 days disappear after the alarm or on opening Trash.
- Folder badge equals the recursive bookmark count.
- Uncaptured bookmarks show a site icon.
- Settings-only export contains no API key; import of a tampered file ignores unknown keys and
  wrong types.
- A multi-id delete with one protected id removes nothing and reports the blocked id.
- An external folder delete (Chrome's manager, UI closed) appears as one Trash row.
- `npm run lint`, `npm test -- --run` and `npm run build` pass.
- Permission gate before upload, run from a throwaway local dev extension that holds the
  `management` permission (never added to this extension):
  `chrome.management.getPermissionWarningsByManifest` returns the same warning list for the
  1.2.0 and 1.3.0 manifests. Manual check: with the unpacked 1.2.0 loaded, replacing it with
  1.3.0 and reloading keeps the extension enabled with no re-approval prompt.
